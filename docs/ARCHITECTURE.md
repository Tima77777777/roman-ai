# Architecture — ROMAN AI (MVP)

Это архитектура MVP-версии проекта, а не всей «AI-компании» из полного ТЗ. Scope сознательно сужен и согласован с владельцем: один бренд (ROMAN), один режим контент-пайплайна (MODE 2 — ROMAN RAW), Telegram как единственный канал команд, GitHub как командный центр. Остальные 8 брендов, MODE 1/3, департаменты Finance/CRM/Legal — вне MVP. Полный текст исходного ТЗ: `docs/TZ_AI_Company_Hybrid.md`. Источник фактов ниже: `docs/TECHNOLOGY_AUDIT.md`.

### 1.2 Иерархия агентов в MVP

Полный ТЗ описывает иерархию Роман → Татьяна (AI COO) → руководители направлений → специалисты → субагенты как отдельные, потенциально постоянно работающие роли. В MVP-объёме (один бренд, одна задача за раз) это **не отдельные сервисы**, а роли внутри ОДНОГО запуска Claude Code:

- **Татьяна** = сам факт того, что Claude Code интерпретирует сообщение Романа и решает, что делать — оркестрирующий слой промпта, не отдельный процесс.
- **Специалисты** (сценарист, монтажёр, QA) = шаги одного и того же пайплайна ROMAN RAW (транскрипция → выделение моментов → сценарий/хук → монтаж → QA), выполняемые последовательно тем же агентом с разными инструментами на каждом шаге.
- **Субагенты** — используются только там, где реально нужна параллельная работа (например: обработка нескольких новых сообщений из Telegram за один прогон, или синтез нескольких кандидатов сценария) — через Agent tool, не как постоянная инфраструктура.

Это осознанное упрощение: выделять реальных отдельных постоянных агентов-департаменты имеет смысл только когда появится больше одного бренда — это Фаза 6 в исходном ТЗ, не сейчас.

### 1.3 Security boundaries на уровне MVP

- **Секреты** (`TELEGRAM_BOT_TOKEN`, GitHub PAT) хранятся только в `.env` локально — файл в `.gitignore`, никогда не коммитится. Для целевой облачной Routine секрет передаётся как часть конфигурации routine на стороне claude.ai (видна только владельцу аккаунта), не как часть кода репозитория.
- **Owner allowlist**: и локальный поллер, и целевая Routine обрабатывают команды только от `TELEGRAM_OWNER_ID = 8796085265` — сообщения от любого другого Telegram-пользователя молча игнорируются.
- **Необратимые действия** (платные подписки, новые учётные данные, архитектурные изменения) — агент обязан НЕ выполнять их автономно, а зафиксировать в отчёте Роману как требующие решения. Это применяется на уровне промпта исполнителя (см. `docs/adr/003-automation-executor.md`), а не проверяется отдельным кодом — это осознанное ограничение MVP, ужесточить в Implementation Plan P1.
- **Видимость репозитория**: репозиторий временно **public** (см. `docs/adr/003-automation-executor.md` — причина: не удалось подключить GitHub App к claude.ai Routines через доступный UI). Секреты это не затрагивает (см. выше), но текст ТЗ и вся бизнес-стратегия сейчас публично читаемы. Возврат к private — первая задача после решения проблемы с GitHub App (см. Implementation Plan, P0).
- **Публикация на площадки**: OAuth-токены YouTube/Facebook/Instagram/TikTok API будут храниться так же, как Telegram-токен — в `.env`, не в репозитории; для облачного исполнения — в переменных окружения Routine/GitHub Actions secrets, не в коде.

## 3. Командный центр: Telegram + GitHub

### 3.1 Текущее рабочее состояние (в проде прямо сейчас)

Механизм — локальный опрос без вебхуков:

1. `CronCreate`-задача внутри активной Claude Code сессии срабатывает каждые 7 минут.
2. Читает `state/telegram_offset.json` — число `offset` (id последнего обработанного Telegram-апдейта).
3. Запрашивает `GET https://api.telegram.org/bot<TOKEN>/getUpdates?offset=<offset+1>` — Telegram возвращает только апдейты новее сохранённого offset (стандартный паттерн Bot API, без него старые сообщения возвращались бы повторно).
4. Фильтрует по `message.from.id == TELEGRAM_OWNER_ID` — сообщения от кого угодно другого игнорируются, но их `update_id` всё равно учитывается при пересчёте offset (иначе они будут возвращаться повторно бесконечно).
5. Если новых сообщений от владельца нет — выполнение молча завершается (нет коммитов, нет сообщений в Telegram — не спамит).
6. Если есть — задача выполняется тем же агентом (Read/Write/Edit/Bash в рамках репозитория), результат коммитится и пушится в `main`. Push идёт через обычный `git push origin main` — репозиторий настроен на repo-scoped credential helper через `gh` (`git config credential.https://github.com.helper "!gh auth git-credential"`), токен читается из `.env` в переменную окружения перед вызовом, а не вставляется в текст команды/URL (см. раздел 1.3, `SECURITY.md`).
7. `state/telegram_offset.json` обновляется и коммитится.
8. Ответ уходит Роману через `POST .../sendMessage`.

**Ограничение**, зафиксированное честно: это работает, только пока жива именно эта Claude Code сессия (ноутбук включён, процесс не завершён). Задача автоматически истекает через 7 дней (ограничение самого механизма `CronCreate` — сессионные задачи не пишутся на диск).

### 3.2 Целевое состояние (не запущено — заблокировано на этапе UI)

Согласно Technology Audit, правильная архитектура — **Cloudflare Worker как webhook-мост** + **Claude Code Cloud Routine** как исполнитель, что даёт независимость от ноутбука владельца и (потенциально) near-realtime реакцию вместо cron-задержки:

```
Telegram (setWebhook) → Cloudflare Worker → POST /repos/.../issues (GitHub REST API)
                                                        │
                                          issue: opened │ НЕ поддерживается нативным
                                                        │ GitHub-триггером Routines
                                                        ▼
                                          GitHub Actions workflow (issues: opened)
                                                        │
                                          curl POST bearer-защищённый
                                          /v1/claude_code/routines/{id}/fire
                                                        ▼
                                          Claude Code Cloud Routine выполняет задачу
```

**Блокер снят (2026-09-01).** Причина 401 оказалась именно в том, что подозревалось: у аккаунта не было установлено GitHub App. Решение нашлось не в Settings → Connectors (тот коннектор — отдельный, не про Routines), а на самой странице **claude.ai/code → New** — там прямым текстом показывался чеклист "Two steps to work in your repo" с кнопкой **"Install on GitHub"** (Connect account был уже готов, не хватало именно этого второго шага). Установлено с ограничением на конкретные репозитории (`roman-ai`, `fin-tracker-bot`), не на все.

**Cloud Routine создана и подтверждена реальным прогоном.** `RemoteTrigger.create` (прямой вызов API, без браузера) поначалу требовал `job_config.ccr.environment_id` — такого окружения через API не создать, обнаружилось через claude.ai/code → New → выбор репозитория → Cloud → "Add cloud environment...". Там же выяснилось важное ограничение: поле "Environment variables" **не подходит для секретов** ("visible to anyone using this environment") — но отдельного secrets-хранилища в текущем UI нет, так что токен всё равно кладётся туда (для одиночного аккаунта это равносильно "виден только тебе самому", риска утечки третьим лицам нет; в git не попадает, хранится в бэкенде Anthropic).

Routine "Telegram poller" (`trig_019Gn3cnxtPVQrADrG4XuXrX`) создана с cron `33 * * * *` (раз в час), окружением `roman-ai` (переменные `TELEGRAM_BOT_TOKEN`, `TELEGRAM_OWNER_ID`, `Network access: Full`). **Тестовый прогон (`Run now` через API) завершился успешно**: агент сам прочитал `docs/ARCHITECTURE.md` и `policy.json` для контекста, проверил переменные окружения, обратился к Telegram `getUpdates` с реальным токеном, получил пустой список (новых сообщений не было) и корректно ничего не закоммитил — ровно то поведение, что описано в шаге 5 ниже. По пути поймали и исправили реальную ошибку (не архитектурную — просто человеческий фактор): в переменные окружения по невнимательности сначала попал токен от ДРУГОГО бота (fin-tracker-bot) — агент упёрся в `409 Conflict` от Telegram (webhook у чужого бота активен), сам расследовал причину вместо того чтобы упасть вслепую, что и вскрыло ошибку.

**Оставшийся шаг** — GitHub Actions workflow `issue opened → Routine /fire` (пункт 5 ниже) всё ещё не написан, поэтому Cloudflare-мост `telegram-bridge` намеренно не подключён к реальному вебхуку бота (см. `apps/telegram-bridge/README.md`). Вместо него теперь основным каналом стала сама Cloud Routine — она не нуждается в мосте вообще, поскольку `RemoteTrigger` с cron-расписанием уже и есть облачный аналог локального поллера. Локальный `CronCreate`-поллер можно считать замененным.

1. ✅ Подключить GitHub App к Routines — сделано (2026-09-01).

Не используется как основной канал — Cloud Routine оказалась достаточной сама по себе; мост остаётся как задел на случай, если понадобится near-realtime реакция вместо почасового расписания.
