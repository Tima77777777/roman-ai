## Context

## Context

Требование владельца с самого начала — работа "независимо от того, включён ли ноутбук". Technology Audit зафиксировал три реальных варианта:

1. **Claude Code Cloud Routines** (`RemoteTrigger` API) — облачные, но статус LIMITED/research preview; создание Routine для приватного репозитория потребовало подключения GitHub App к аккаунту claude.ai, которое не удалось найти/выполнить через доступный UI за разумное время (см. `docs/ARCHITECTURE.md`, раздел 3.2, и попытку — `401 Connect your GitHub account`).
2. **Официальный Telegram-плагин Claude Code Channels** — требует постоянно запущенного локального процесса (`claude --channels ...`), архитектурно противоречит требованию независимости от ноутбука. Отклонён.
3. **Локальный `CronCreate`-поллер** внутри интерактивной сессии — работает сразу, без внешних зависимостей, но живёт только пока сессия открыта, автоматически истекает через 7 дней.

## Decision

**Двухфазный подход:**
- **Сейчас (Phase 0 fallback):** локальный `CronCreate`-поллер каждые 7 минут — работающее решение на период, пока не решён вопрос с GitHub App.
- **Целевое (Phase 1):** Claude Code Cloud Routine (cron `13 * * * *`, минимум раз в час) как замена поллеру, плюс Cloudflare Worker + GitHub Actions мост (код уже написан — `apps/telegram-bridge/`, описание — ARCHITECTURE.md раздел 3.2) для near-realtime реакции вместо часовой задержки.

Переход на Routine — первая P0-задача в Implementation Plan, не откладывается на потом.

## Consequences

- До перехода: реальный риск простоя автоматизации, если ноутбук/сессия выключены дольше 7 дней или до следующего запуска Claude Code — владелец должен об этом знать (зафиксировано в `docs/ARCHITECTURE.md`).
- После перехода: полная независимость от локального устройства, соответствует изначальному требованию.
- Routine остаётся в статусе research preview (по данным аудита) — закладывать риск изменения API/лимитов в план, не считать гарантированным SLA.
- Любые задачи, требующие необратимых действий (оплата, новые credentials, архитектурные изменения) — исполнитель (в любой из двух фаз) обязан НЕ выполнять их автономно, а фиксировать в отчёте Роману. Формализовано как проверяемый whitelist — `policy.json` + `scripts/policy_check.py` (P1, реализовано).
